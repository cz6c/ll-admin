# c-defense

只解决一个问题：**防御应该设在哪里**。

## 核心公理

1. **静态类型 ≠ 运行时保证** — 外部流入数据不受 TS/类型注解保护。  
2. **可信域 vs 不可信边界** — 内部信任类型；边界必须运行时校验。  
3. **两类错误** — 逻辑错误尽早暴露；外部输入错误校验、记日志、可控拒绝。  
4. **过度防御** — 可信域内重复判空、无脑兜底、吞掉全部异常。

## 决策总纲

1. 可信域：依赖类型与编译检查，不手写运行时类型校验。  
2. 不可信边界：强制校验；优先 class-validator / Zod 等，不堆 if。  
3. 异常：IO/外部可捕获并记录；内部业务逻辑勿静默吞掉。  
4. 断言不校验外部输入（生产可被关掉）。  
5. 禁止 `catch` 后静默返回默认值掩盖缺陷。

## 不可信边界清单

HTTP 响应 · JSON 反序列化 · 文件 · 配置 · DB 结果 · 环境变量 · 第三方 SDK · **Tauri `invoke` 返回** · 用户输入。

## 本仓衔接

| 位置 | 做法 |
|------|------|
| Nest DTO | class-validator；Controller 信任校验后的 DTO |
| admin `$http` | 类型来自 `#/api`；边界异常走统一 request/feedback，勿页内吞掉 |
| Tauri | `invoke` 结果当外部输入；错误向上抛或明确 UI 提示 |
| 可信域内部 | 少写 `?.`/`as` 连环兜底 |

## Checklist

1. 当前代码是可信域还是边界？  
2. 可信域有无多余判空/静默兜底？  
3. 边界是否结构化校验？  
4. catch 是否只限 IO/外部且有日志？  
5. 有无 `as` 强转欺骗编译器？
